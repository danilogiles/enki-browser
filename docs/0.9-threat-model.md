# 0.9 Receive tabs: threat model (Cloak)

Scope: an agent sends a packet (title, summary, 1-10 links); Enki asks; on Accept it opens a tab group on hold.html. 0.9 never sends browser data to the agent.

## Assets
Danilo's browsing data, session cookies, the per-agent keys, his attention (spam), and the fact that he received/opened something.

## Threats and required mitigations

1. Spoofed or stolen sender
   - One key pair per agent (signature + encryption), created at pairing. Pairing code: single use, 5 min, high entropy.
   - Pairing is confirmed in Enki showing the agent name and a short fingerprint that the agent side also shows. Never auto-accept a pairing.
   - Agent private key lives only in the MCP server's secret store / env, never in chat or the repo.
   - Unpair deletes that agent's key and mailbox; one compromised agent never affects the others.

2. Malicious or compromised relay
   - Relay only sees ciphertext, a random per-pairing mailbox id, size and timing. No account, name or email tied to the mailbox.
   - Pad ciphertext to a fixed size so link count/summary length do not leak.
   - Delete on fetch, 10 min TTL, no logs. Relay URL must be https.
   - Replay/delay: every packet has a nonce and timestamp inside the signed part; Enki rejects seen nonces and anything older than 10 min.
   - Size cap (e.g. 16 KB) checked before decrypting.

3. Malicious links
   - Only http/https. Reject javascript:, data:, file:, blob:, chrome:, chrome-extension:, intent: and URLs with user:pass@.
   - Show the domain in ASCII (punycode) when it is an IDN, so lookalike domains are visible.
   - Every link goes through Enki Shield before the notice is shown; one blocked link rejects the whole packet.
   - Tabs open on hold.html: no network request to the site until the user clicks Open. No favicon, thumbnail or preview. No downloads triggered.

4. Prompt injection through title/summary/labels
   - Rendered as plain text (textContent), no HTML or Markdown.
   - Strip control characters and bidi overrides (e.g. U+202E) from title, labels and summary.
   - The summary is never added to the assistant's context or treated as an instruction unless the user explicitly asks the assistant about it, and then it is marked as untrusted data.

5. Spam / denial of service
   - Master switch off by default. Max 5 packets/hour per agent, 3 pending notices; extras dropped silently.
   - No notices in incognito windows; groups only open in normal windows.

6. Leaking to the sender
   - No read receipts: the sender never learns whether a packet was accepted, declined or opened. Relay deletes on fetch regardless of the decision.
   - The poll carries only the mailbox id and a request signature, no browsing data.

7. Local storage and permissions
   - Keys stored as non-exportable WebCrypto keys in the profile. The 50-packet log stays local and is cleared with Clear browsing data and on unpair.
   - New permissions limited to alarms, tabGroups and host access to the relay origin only. No history, no <all_urls>, no reading other tabs.
   - PRIVACY.md updated in the same PR (what the relay sees, retention, self-hosting).

## Tests that must pass before merge
- Packet with a bad or unpaired signature: rejected, nothing opens.
- Replayed packet / packet older than 10 min: rejected.
- javascript:, data:, file: and user:pass@ links: rejected.
- Link blocked by Shield: whole packet rejected.
- 6th packet in an hour / 4th pending notice: dropped.
- Summary containing HTML and a bidi override: shown as plain text, override stripped.
- hold.html makes zero requests to the target site before Open (check with the network log).
- Unpair: the agent's key, mailbox and log entries are gone; its next packet is rejected.

## Phase 2 (sharing a tab back to an agent), not in 0.9
Show the exact payload before it leaves; never send cookies, passwords, form data or incognito tabs; PRIVACY.md update first.
